# Terraform - EKS and supporting AWS infrastructure

Provisions everything the POS platform needs on AWS: a VPC, an EKS cluster, ECR
repositories, RDS Postgres, ElastiCache Redis, optional MSK, an S3 bucket for
batch output, and Secrets Manager wiring via IRSA.

> **Validated, not applied.** `terraform fmt`, `init` and `validate` all pass
> against Terraform 1.10.5 with the real providers and modules downloaded.
> `terraform plan` and `apply` have **not** been run - that needs AWS
> credentials and creates billable resources. Treat the first `plan` as the real
> review. See *Before you apply* below.

## Layout

```
infrastructure/terraform/
├── versions.tf         provider + Terraform version constraints
├── backend.tf          S3 remote state (partial config)
├── providers.tf        aws, kubernetes, helm
├── variables.tf        all inputs
├── locals.tf           naming, tags, subnet maths
├── vpc.tf              VPC, subnets, NAT, VPC endpoints
├── eks.tf              cluster, node group, addons, storage class
├── irsa.tf             IAM roles for service accounts
├── ecr.tf              one repository per service
├── data-stores.tf      RDS, ElastiCache, MSK
├── storage-secrets.tf  S3 bucket, Secrets Manager, External Secrets
├── outputs.tf
└── envs/
    ├── dev.tfvars      + dev.backend.hcl
    └── prod.tfvars     + prod.backend.hcl
```

A single root module with per-environment `.tfvars` and separate state keys.
Chosen over a `modules/` + `envs/` split because there is one stack here, and
premature module extraction mostly buys indirection.

## Bootstrap

Terraform cannot create the bucket that stores its own state, so that comes
first, once per account:

```bash
aws s3api create-bucket \
  --bucket pos-terraform-state-<account-id> \
  --region ap-south-1 \
  --create-bucket-configuration LocationConstraint=ap-south-1

aws s3api put-bucket-versioning \
  --bucket pos-terraform-state-<account-id> \
  --versioning-configuration Status=Enabled

aws s3api put-bucket-encryption \
  --bucket pos-terraform-state-<account-id> \
  --server-side-encryption-configuration \
  '{"Rules":[{"ApplyServerSideEncryptionByDefault":{"SSEAlgorithm":"AES256"}}]}'
```

Versioning is not optional. State is the only record of what exists, and a
corrupted apply with no previous version is a manual reconciliation against the
live account.

Then set the bucket name in `envs/*.backend.hcl`.

## Usage

```bash
cd infrastructure/terraform

terraform init -backend-config=envs/dev.backend.hcl
terraform plan  -var-file=envs/dev.tfvars
terraform apply -var-file=envs/dev.tfvars

aws eks update-kubeconfig --region ap-south-1 --name pos-dev-eks
```

Switching environments requires re-initialising the backend:

```bash
terraform init -reconfigure -backend-config=envs/prod.backend.hcl
```

## After apply

Three things are installed with Helm rather than Terraform, because a Helm
release and the cluster it installs into are cleaner to manage in separate
applies:

```bash
# External Secrets Operator - required before pos-secrets can be created
helm repo add external-secrets https://charts.external-secrets.io
helm install external-secrets external-secrets/external-secrets \
  -n external-secrets --create-namespace \
  --set serviceAccount.annotations."eks\.amazonaws\.com/role-arn"=$(terraform output -raw -json irsa_role_arns | jq -r .external_secrets)

# AWS Load Balancer Controller - Ingress resources stay Pending without it
helm repo add eks https://aws.github.io/eks-charts
helm install aws-load-balancer-controller eks/aws-load-balancer-controller \
  -n kube-system \
  --set clusterName=$(terraform output -raw cluster_name) \
  --set serviceAccount.create=false \
  --set serviceAccount.name=aws-load-balancer-controller

# Argo Rollouts - required by check-service-rollout.yml
kubectl create namespace argo-rollouts
kubectl apply -n argo-rollouts -f \
  https://github.com/argoproj/argo-rollouts/releases/latest/download/install.yaml
```

## What this fixes

Several findings from the Kubernetes manifests are resolved at the
infrastructure layer rather than papered over:

| Existing problem | Fixed by |
| ---------------- | -------- |
| DB password and JWT key in plaintext in `configmap.yml` | Secrets Manager + External Secrets + IRSA. RDS generates and rotates its own password; the JWT key is generated by Terraform and never printed. |
| `image: ...:latest` with no rollback target | ECR with `image_tag_mutability = "IMMUTABLE"` |
| `serviceAccountName: pos-service-account` referenced but never defined | Created in `irsa.tf`, so pods can actually schedule |
| cook-service batch output on pod-local `emptyDir` | S3 bucket + a scoped IRSA role |
| Kubernetes Secrets unencrypted in etcd | `cluster_encryption_config` with a customer-managed KMS key |
| Nothing restricts pod → cloud credentials | IMDSv2 required, hop limit 1, so a compromised pod cannot assume the node role |

## Before you apply

- **`image_tag_mutability = "IMMUTABLE"` breaks the current pipeline.**
  `check-service/Jenkinsfile` pushes both an immutable tag and `:latest`. The
  second build's `:latest` push will be rejected. Remove that push - the
  pipeline already computes `${BUILD_NUMBER}-${GIT_COMMIT}`.
- **External Secrets custom resources are not in Terraform**, deliberately. A
  `ClusterSecretStore` is an instance of a CRD that only exists after the
  operator is installed, and `kubernetes_manifest` validates against the live
  API at *plan* time - so planning against a cluster that does not exist yet
  fails outright. They live in
  `infrastructure/kubernetes/external-secrets.yml` and are applied after the
  operator, with two values substituted from Terraform outputs.
- **Postgres 15.7 and Redis 7.1** are pinned to match `docker-compose.yml`.
  Verify both are still offered in your region before applying.
- **The default `cluster_endpoint_public_access_cidrs` is `0.0.0.0/0`.** Still
  authenticated, but narrow it to your office or VPN range.

## Cost

Rough order of magnitude, ap-south-1, before data transfer:

| Component | dev | prod |
| --------- | --- | ---- |
| EKS control plane | ~$73/mo | ~$73/mo |
| Nodes | 2 × t3.large spot, ~$25/mo | 3 × m6i.large on-demand, ~$210/mo |
| NAT gateway | 1, ~$32/mo | 3, ~$97/mo |
| RDS | t4g.micro, ~$13/mo | m6g.large Multi-AZ, ~$250/mo |
| ElastiCache | t4g.micro, ~$12/mo | m6g.large × 2, ~$200/mo |
| MSK | disabled | 3 × kafka.m5.large, ~$400/mo |

Dev lands around **$155/month**, prod around **$1,230/month**. MSK is the single
largest line item and the reason `enable_msk` defaults to false.

`terraform destroy` fully tears down dev. Prod has `deletion_protection` on RDS
and a final snapshot, so it will refuse - deliberately.

## Not included

- **OpenSearch** for the ELK pipeline. Add it as a toggled resource following
  the `enable_msk` pattern, or point Logstash at Elastic Cloud.
- **Route53 / ACM.** The ingress still uses the `pos.local` host with no TLS.
- **Karpenter.** The managed node group plus cluster-autoscaler IRSA is the
  simpler starting point; Karpenter is the upgrade once node shapes vary.
- **Multi-region.** Single region, multi-AZ. Multi-AZ handles the overwhelming
  majority of real failures and is the right first rung.
